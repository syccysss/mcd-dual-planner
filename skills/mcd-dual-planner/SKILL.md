# 麦麦双赢 · 配餐技能

把「省钱」和「吃得对」当成同一个约束优化问题的两个目标来解，而不是二选一。

## 何时使用

用户提出下列任何一类需求时使用本技能：

- 「我预算 30 块，帮我点一餐麦当劳」/「怎么点最省钱」
- 「减脂期想吃麦当劳，700 大卡以内、蛋白质要够」
- 「帮我控一下钠，午餐别太咸」
- 「这些券怎么用最划算，帮我比一下」
- 「同样 30 块，是巨无霸划算还是两个吉士汉堡划算」

## 前置条件

1. WorkBuddy 已配置并**信任**麦当劳 MCP Server：
   - URL：`https://mcp.mcd.cn`，类型 `streamablehttp`
   - 请求头：`Authorization: Bearer <用户自己的 MCP Token>`
   - 配置模板见项目根目录 `mcp-config.example.json`（只有 `${MCD_MCP_TOKEN}` 占位符）
2. Token 由用户在 https://open.mcd.cn/mcp 申请（登录 → 控制台 → 激活 → 复制）。
3. 配置后在【专家·技能·连接器】→【连接器】→【自定义连接器】里找到 `mcd-mcp` 并**启用**，
   然后刷新或重启会话；否则当前会话看不到麦当劳工具。
4. **不要在对话中展示、复述或记录用户的 Token。**

## 工作流

### 第 1 步：确认目标（缺什么问什么，不要自己编）

必须要到的三个输入：

| 输入 | 缺省建议 | 说明 |
|---|---|---|
| 预算（元） | 30 | 每餐上限 |
| 热量目标（kcal） | 700 | 成年人的一餐参考值 |
| 蛋白质下限（g） | 30 | 减脂/健身场景尤其重要 |

可选：钠上限（缺省 1200 mg）、取餐方式（到店自取 / 外送 / 得来速）、门店或城市。

### 第 2 步：取真实数据（只读）

按顺序调用，**不要跳过**：

1. `now-time-info` —— 拿服务器时间，用于判断券与活动的有效期，不要用本地时间猜。
2. `query-nearby-stores` —— 用「城市 + 门店名/地标」搜索（`searchType=2`）；
   取餐方式 `beType=1` 到店自取、`5` 得来速。记下门店编码。
3. `query-meals` —— 拉当前门店菜单，得到商品编码、价格、品类。
4. `list-nutrition-foods` —— 拉官方营养库。
5. `query-meal-detail` —— 对「套餐」类商品，取出组成项，把单品营养**累加**成套餐营养。
6. `query-store-coupons` / `available-coupons` / `query-my-coupons` —— 取可用券，**只查询，不领取**。
7. `calculate-price` —— 对最终推荐的 3 个方案调用，用官方实付核验本地菜单价合计。

### 第 3 步：把菜单项与营养对上

- 名称规范化后再匹配：去掉括号内容、规格词（中杯/大杯/套餐/单份）、标点与空格，再比对。
- 匹配顺序：完全相同 → 一方包含另一方 → 字符重合度 ≥ 0.72。
- **匹配不上就当作"营养未知"，把该餐品排除在计算之外，并明确告诉用户排除了多少项。**
  绝对不要用相似餐品的营养值代替，也不要凭常识估一个数。

### 第 4 步：求解（心算或调用项目脚本）

营养得分（0~100）：

```text
热量贴合 = clamp(1 − |实际热量 − 目标热量| / (目标热量 × 容差), 0, 1)     // 容差默认 20%
蛋白达成 = min(实际蛋白 / 目标蛋白, 1)，超过目标最多加 0.15 的奖励
脂肪控制 = clamp(1 − max(0, 实际脂肪 − 脂肪上限) / 脂肪上限, 0, 1)        // 上限默认 = 目标热量×35%/9
钠惩罚   = min(1, max(0, 实际钠 − 钠上限) / 钠上限) × 25

得分 = clamp(100 × (0.40×热量贴合 + 0.45×蛋白达成 + 0.15×脂肪控制) − 钠惩罚, 0, 100)
```

求解三件事：

1. **双赢推荐**：达到营养门槛（默认 70 分）的方案里，**实付最低**的那个；
2. **营养上限**：预算内得分最高的那个；
3. **省钱底线**：预算内实付最低的那个。

品类规则默认：1 个主食 + 0~2 个小食 + 0~1 个饮料 + 0~1 个甜品。
需要更精确的最优解时，可以调用项目脚本（见下）。

### 第 5 步：输出

用**表格 + 一句话结论**回答，必须包含：

- 三个方案的餐品明细、实付金额、热量、蛋白质、钠、营养得分；
- **为什么推荐它**（例如「达标方案里最便宜的，比第二名省 4 元但蛋白质少 3 g」）；
- 官方算价与本地菜单价的差异（若有）；
- 数据口径：营养匹配上多少项、排除了多少项、每个方案用了哪张券（券已纳入求解，按券后实付排序）、券按订单级满减估算。

## 可以调用的项目脚本

本技能对应的开源实现对同一套口径做了实现，需要严格最优解或多方案对比时可以调用：

```bash
# 离线自检（无需 Token）
node bin/mcd-dual.mjs doctor

# 用真实 Token 求解并生成 SVG 战报
node bin/mcd-dual.mjs plan --budget 30 --kcal 700 --protein 30 --sodium 1200 \
  --city <城市> --store <门店关键词> --out reports/report.svg
```

脚本同样**只读、不下单**；战报中的每个数字都可追溯到具体工具调用。

## 安全规则

- **只读**：不调用 `create-order`、`mall-create-order`、`auto-bind-coupons`、`draw-lottery`、
  `party-order-create`、`delivery-create-address` 等写入类工具。用户要下单，引导其到官方 App/小程序
  自行确认支付。
- **不替用户决策高风险项**：不要默认帮用户选最贵的方案，也不要在用户没有明确同意时领券。
- **不泄露凭据与个人信息**：不复述 Token，不展示手机号、地址、订单号。
- **不承诺优惠一定可用**：券的可用性以官方算价与下单页为准。

## 常见坑

- **单位**：菜单与算价金额单位是**分**，展示给用户前要换算成元；能量可能是 kJ，钠可能是 g，
  需要换算时**要说明这是换算后的值**。
- **`searchType`**：收藏餐厅为空时不要硬撑，改用「城市 + 门店名/地标」搜索（`searchType=2`）。
- **`beCode` 不是所有场景都返回**：到店自取的门店可能没有 `beCode`，此时后续查询不要传该参数。
- **不要对 429 循环重试**：官方限流是 600 请求/分钟，重试只会更糟，应降低频率后重试。
- **营养匹配失败很常见**：这是正常情况，如实告知并排除，比编一个数字安全得多。

## 验证清单

交付前自查：

1. 三个方案都**真的**在预算内？
2. 每个数字都能说清来自哪个工具？
3. 营养未知的餐品是否已排除并告知数量？
4. 是否复述过 Token 或个人信息？（必须是"没有"）
5. 是否明确说明「非麦当劳官方产品、以官方渠道结果为准」？
