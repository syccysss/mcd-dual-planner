## 4. 多门店跨城实时验证（2026-10-10，8 城）

单店跑通只能证明「算法在某家门店的数据上没崩」，不能证明它跨价格体系、跨菜单依然可靠。
本轮对 **8 个城市各取 1 家门店**做了完整实时求解（同一份代码、同一组参数：预算 ¥40、
热量 700 kcal ±20%、蛋白 ≥30 g、钠 ≤1200 mg），每家都做官方组合价核验。

```bash
node tools/batch-verify.mjs --budget 40   # 8 城 × 1 店；首次约 800 次请求 / 4 分钟，
                                          # 菜单缓存命中后约 176 次 / 1.5 分钟
```

「验价」= 本地菜单价合计与官方 `calculate-price` 返回的组合价完全一致。

**这一轮暴露并修掉的问题**：北京 / 深圳 / 武汉 三家门店的候选规模（74~79）会撞上 40 万方案的枚举上限。
原先的做法是「枚举到一半直接砍断」——但枚举是按品类顺序深度优先展开的（主食在最外层），
被砍掉的永远是**排在候选列表后面的主食**，也就是价格更高、蛋白往往更高的那些选项，
于是结果被**系统性地偏向便宜主食**，「营养上限」这个结论会被算歪。
现已改为：一旦触发上限就**自动下调候选规模重算**（`stats.perCategoryAdjusted` 留痕、终端与战报如实显示），
用「候选略少但枚举完整」换掉「候选多但结果有偏」。三家门店均自动 6→5，最终 **8 城全部无截断**。

**跨城价格是真的不一样**：140 款各城都有的同款商品里，**42 款存在城市间价差**。
最大价差出现在套餐上，例如「全明星双人分享餐八件套」¥114.5（上海/武汉）~ ¥117.5（成都），
「巨无霸四件套」¥58.5 ~ ¥59.5。这正说明**必须按门店实时取价**——用一份"全国统一价表"算出来的结论，
在城市层面就是错的。

**结论的跨城一致性（这才是重点）**：8 个城市的双赢推荐都落在 **¥29~30**、省钱底线都在 **¥13.9~14**、
营养上限在 **¥38.5~40**。同一份代码在 8 个不同门店给出高度一致的结论，说明结果不是
「恰好对某家店调出来的参数」，而是由菜单结构决定的。

## 5. 取餐方式与同城多店验证（2026-10-10）

**换个取餐方式还成不成立？同一个城市里换一家店，结论还一样吗？**


### 5.1 三种取餐方式对照

| 取餐方式 | 样本 | 菜单规模 | 营养匹配 | 截断 | 验价 | 餐品价跨店/跨城价差 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|
| 到店自提 `beType=1` | 成都 × 3 店 | 59 ~ 122 | 56% ~ 61% | 无 | ✅ 全部一致 | **110 款可比中 38 款有价差**（最大 ¥9.5，**同城之内**） |
| 麦乐送 `beType=2` | 北京 / 上海 | 122 / 131 | 59% / 58% | 无 | ✅ 全部一致 | **114 款可比中 0 款有价差**（全国统一定价） |
| 得来速 `beType=5` | 成都 / 北京 | 124 / 112 | 59% / 63% | 无 | ✅ 全部一致 | 96 款可比中 41 款有价差 |

三个反直觉的结论：

1. **同城之内也不止一套价**。成都三家门店里，110 款同款商品有 38 款价格不同，最大差 ¥9.5
   （「全明星双人分享餐八件套」¥117 / ¥117.5 / ¥126.5）。所以「按城市查价」都不够，
   **必须落到门店**——这正是本项目坚持逐门店实时取价的原因。
2. **麦乐送的餐品价是全国统一的**（114 款可比商品 0 价差），但**到手价并不统一**：
   配送费 ¥6 + 打包费随组合浮动（见 5.2）。统一的是菜价，不统一的是总支出。
3. **门店规模差异极大**：同城三家店里有一家只有 59 项菜单（另两家 115 / 122），
   营养匹配数 35 / 64 / 74，达标方案数 10 / 36 / 24。**换一家店，可选范围几乎腰斩。**

### 5.2 外送成本口径：为什么配送费不摊进单品价

官方麦乐送 `calculate-price` 的真实返回结构（实测）：

```
productPrice    13260   餐品价
deliveryPrice     600   配送费（7 次调用恒为 ¥6）
packingPrice      300   打包费（随组合变化：0 / 190 / 300）
packingOriginalPrice 570
price           14160   = 餐品 + 配送 + 打包  ← 官方总价
```

**打包费随商品组合变化**（可打包商品 ¥1.90/件、上限 ¥3.00，实测拟合："汉堡包"单品无一元打包费）。
因此把「配送 + 打包」当成整单常数会导致部分方案多算或少算 —— 实测偏差 0.80 元。

> 这里修正了一个**先前的实现错误**：早先版本按猜测的字段名 `deliveryFee / freight / shippingFee`
> 解析配送费，而真实字段是 `deliveryPrice / packingPrice`，导致这两个值**恒为 `null`**、
> 配送费被静默忽略。该 bug 已修复，并补上单元测试。

**当前采用的口径**（宁可慢、不可假）：

- 预算与择优只认**餐品价**（逐品官方算价，精确，不掺估算）；
- 每个推荐方案的**到手价**由官方算价**单独核验**后列出，含配送费与打包费；
- 到手价超出预算时**显式告警**（实测北京麦乐送预算 ¥50 时，「营养上限」餐品 ¥48 + 配送 ¥6 + 打包 ¥2.7 = ¥56.70，终端与战报均打 ⚠）。

北京麦乐送实测（预算 ¥50）：

| 结论 | 餐品价 | 配送费 | 打包费 | **到手价** | 验价 |
|---|:--:|:--:|:--:|:--:|:--:|
| 双赢推荐（双层深海鳕鱼堡 + 菠萝派） | ¥35.50 | ¥6.00 | ¥1.90 | **¥43.40** | ✅ |
| 营养上限（汉堡包 + V翅 + 奥利奥麦旋风） | ¥48.00 | ¥6.00 | ¥2.70 | **¥56.70** ⚠ 超预算 | ✅ |
| 省钱底线（汉堡包） | ¥15.00 | ¥6.00 | ¥1.10 | **¥22.10** | ✅ |

### 5.3 这一轮修掉的缺陷：`beType` 名义上支持、实际跑不通

`beType` 是 CLI 早已暴露的参数，但实测**只有到店（1）能跑**，另外两种是静默失败：

| 现象 | 根因 | 修法 |
|---|---|---|
| 麦乐送（2）「未查询到门店」 | `query-nearby-stores` 的官方 `beType` 枚举**只有 1、5**。官方外送链路是 `delivery-query-addresses` → `addressId` → `delivery-query-stores`，代码从未调用这条链路 | 按取餐方式分流门店来源；官方强制 `orderType=2` |
| 得来速（5）空菜单 | 得来速门店返回**两个不同编码**（`storeCode=3450230`、`beCode=345023041`），`normalizeStores` 把二者压成一个 `code` 并优先取 `beCode`，再把它塞进 `storeCode` 参数 → 官方返回空菜单 | `storeCode` 与 `beCode` 分开保存、分别传参 |

> 隐私边界：外送链路必须先取账号下的收货地址。本项目**只取地址编号**用于选址，
> 收货人、手机号、门牌在归一化阶段即被丢弃（有单元测试断言），地址编号也不写入任何快照。

## 6. 深度边界审计（2026-10-10）

```bash
node tools/deep-audit.mjs     # 零 MCP 请求，全部基于已抓取的门店快照重算
```

把参数推到极限，逐条断言「诚实性」——**无解时说有解、截断时当完整、退化时不声明**，
是这类工具最危险的失败方式：

| 断言 | 结果 |
|---|:--:|
| 预算极低时如实报「无解」（¥5 时不硬凑推荐） | ✅ |
| 预算单调性（预算↑ ⇒ 预算内方案数不降、省钱底线不升） | ✅ |
| 价格非负（券不会把实付算成负数） | ✅ |
| 标称 `hard-targets` 时双赢推荐确实满足用户硬目标 | ✅ |
| 搜索截断必被标记 | ✅ |
| 自动降级必被记录（`perCategoryAdjusted` 留痕） | ✅ |
| 降级后不再截断 | ✅ |
| 可复现性（同参数两次求解结果完全一致） | ✅ |
| 券折扣金额合理（0 ≤ 折扣 ≤ 订单金额） | ✅ |

**参数推到边界后得到的真实结论**（这些比"能跑"有用得多）：

| 用户设定 | 是否有方案满足 | 实际给出的双赢推荐 |
|---|:--:|---|
| 蛋白 ≥20 g | ✅ | ¥30.00，30 g 蛋白 |
| **蛋白 ≥45 g** | ❌ **无方案满足** | 退化为"最接近的一档" ¥33.00，仅 30 g 蛋白 |
| **蛋白 ≥60 g** | ❌ **无方案满足** | 退化为"最接近的一档" ¥35.50，仅 31 g 蛋白 |
| **钠 ≤600 mg** | ❌ **无方案满足** | 退化为"最接近的一档" ¥33.00，1076 mg 钠 |
| 热量容差 ±5% | ✅ | ¥33.00 |

> 换句话说：**在麦当劳点一份「可吃的餐」（700 kcal、30 g 蛋白、钠 <1200 mg）大约要 ¥29~30；
> 而「单餐 45 g 蛋白」在这份菜单上基本不可达**——不是算法找不到，而是菜单里没有这种组合，
> 除非点两份主食（但品类规则限定 1 个主食）。
> 这种情况下引擎会退化为「得分门槛」，并在终端与战报上**显式声明「无方案满足全部硬目标」**，
> 绝不会把不达标的方案冒充成达标。

**预算边界**：预算 ¥20 时 8 城**全部**拿不到达标方案；¥30 时每城刚好出现 1 个；¥50 之后
达标方案数量级上升（北京 180 个、上海 145 个）。据此可以给出一条可执行建议：**想让这顿饭达标，预算至少留到 ¥30。**

## 7. 明确不做的验证

| 项 | 原因 |
|---|---|
| 下单、支付、领券、积分兑换、抽奖 | 本项目**只读**，相关工具在代码层被硬性拒绝；这类操作会产生真实扣款，参赛项目不应自动执行 |
| 超大规模（50+ 门店）并行压测 | 会显著消耗请求配额；**8 城 × 1 店 + 同城 3 店 + 三种取餐方式**已足够暴露跨店与跨取餐方式差异（第 4、5 节），再扩大规模对结论无增益 |
| 企业团餐（`beType=6`） | 本项目**明确不支持**：需企业账号资质、无法验证；且本引擎求解的是「单人餐」营养目标，与团餐的多人批量场景不匹配。传 `--be-type 6` 会**直接报错**，不会被当成"另一种外送"静默跑通 |
| 外送配送费/打包费的逐方案精算 | 打包费随商品组合变化，逐方案调用官方算价意味着几十万次请求；改为只对最终 3 个推荐核验（第 5.2 节） |
| 营养数据准确性复核 | 营养值来自官方接口，本项目不复核也不修改，只做单位换算与匹配 |

## 8. 已知偏差

- 演示数据与真实门店数据无关，所有演示结论仅用于验证算法链路；
- **候选集是裁剪后枚举，不是全量穷举**：每品类保留「最便宜 / 蛋白性价比 / 蛋白最高 / 钠最低」四个方向的并集
  （默认各 6 项），所以「最优解」是裁剪后空间内的最优，裁剪规模写在战报里；
- **品类按名称推断**：官方返回的分类字段是菜单促销分区（如「人气热卖」「随心配1+1」「小食甜品/其他」），
  不是功能分类，故不采用；名称推断不到的商品（蘸酱、周边等）落入「其他」并被排除，战报写明；
- **套餐营养只按 `isDefault` 默认组成项累加**：不把可选项算进去；累加结果超出常理（>3000 kcal 等）
  时按"营养未知"处理，而不是拿错数硬算；
- 营养得分为自定义序数指标（权重见 `src/solver.mjs` 的 `DEFAULT_WEIGHTS`），不代表营养学优劣程度；
  **「达标」判定不使用该得分**，而是按用户设定的热量区间 / 蛋白下限 / 钠上限三项硬目标；
- 券按「指定商品用券价」计费（能定位到方案内具体商品时按「原价 − 用券价」计入优惠），
  面额型（如"第二份半价"）与无法定位商品的券一律标注"未量化、不计入优惠"，不猜测金额；实际可用性与最终优惠以官方结算页为准；
- **搜索存在硬上限**（40 万方案）。一旦触发，引擎会自动**下调候选规模重算**（`stats.perCategoryAdjusted` 留痕、
  终端与战报如实显示），而不是返回被砍断的部分枚举 —— 因为枚举是深度优先展开的，截断会系统性偏向排在前面
  的主食候选；只有极端菜单降到最小候选规模仍超限时，才保留截断告警；
- **用户设定的硬目标可能不可达**：如"蛋白 ≥45 g"在本菜单上无解时，引擎退化为「得分门槛」并**显式声明**
  「无方案满足全部硬目标」，给出的是"最接近的一档"而不是达标方案（见第 6 节）；
- **外送场景的预算按餐品价判定，不含配送费/打包费**：打包费随商品组合变化（实测 ¥0 / ¥1.90 / ¥3.00），
  无法在枚举数十万个方案时逐单精算。因此每个推荐方案的**到手价**由官方算价单独核验后列出，
  超出预算会显式告警（见第 5.2 节）—— 即"预算内"指的是**餐品金额**，不是到手总支出；
- **麦乐送依赖账号下已保存的配送地址**：没有地址就无法选址，会明确报错而不是静默换一种取餐方式；
  本项目不会替你创建地址，也**不保存**任何收货信息（只取地址编号用于选址）；
- **企业团餐（`beType=6`）不在支持范围**：它需要企业账号资质（本项目无法验证），
  且本引擎求解的是「单人餐」营养目标，与团餐的多人批量模型不匹配。取餐方式白名单收敛为 `1 / 2 / 5`
  （见 `src/pipeline.mjs` 的 `SUPPORTED_BE_TYPES`），传其它取值一律显式报错。
