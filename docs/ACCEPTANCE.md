## 4. 明确不做的验证

| 项 | 原因 |
|---|---|
| 下单、支付、领券、积分兑换、抽奖 | 本项目**只读**，相关工具在代码层被硬性拒绝；这类操作会产生真实扣款，参赛项目不应自动执行 |
| 多门店批量压测 | 会显著消耗用户账户的请求配额，且对结论无增益 |
| 营养数据准确性复核 | 营养值来自官方接口，本项目不复核也不修改，只做单位换算与匹配 |

## 5. 已知偏差

- 演示数据与真实门店数据无关，所有演示结论仅用于验证算法链路；
- **候选集是裁剪后枚举，不是全量穷举**：每品类保留「最便宜 / 蛋白性价比 / 蛋白最高 / 钠最低」四个方向的并集
  （默认各 6 项），所以「最优解」是裁剪后空间内的最优，裁剪规模写在战报里；
- **品类按名称推断**：官方返回的分类字段是菜单促销分区（如「人气热卖」「随心配1+1」「小食甜品/其他」），
  不是功能分类，故不采用；名称推断不到的商品（蘸酱、周边等）落入「其他」并被排除，战报写明；
- **套餐营养只按 `isDefault` 默认组成项累加**：不把可选项算进去；累加结果超出常理（>3000 kcal 等）
  时按"营养未知"处理，而不是拿错数硬算；
- 营养得分为自定义序数指标（权重见 `src/solver.mjs` 的 `DEFAULT_WEIGHTS`），不代表营养学优劣程度；
  **「达标」判定不使用该得分**，而是按用户设定的热量区间 / 蛋白下限 / 钠上限三项硬目标；
- 券按「指定商品用券价」计费（能定位到方案内具体商品时按「原价 − 用券价」计入优惠），
  面额型（如"第二份半价"）与无法定位商品的券一律标注"未量化、不计入优惠"，不猜测金额；实际可用性与最终优惠以官方结算页为准；
- **实时结论尚未重新联网验价**（见第 3 节的告警），正式提交前需用真实 Token 重跑一次；
- **搜索存在硬上限**（40 万方案）。达到上限时会在终端与战报上显式告警，此时结果基于部分枚举、可能非全局最优。
