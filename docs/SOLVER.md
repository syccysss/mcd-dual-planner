# 双目标配餐模型说明

本文说明麦麦双赢如何把「省钱」与「吃得对」形式化为一个可求解的约束优化问题，
以及为了实现它做了哪些近似、这些近似的代价是什么。

---

## 1. 问题形式化

### 1.1 符号

| 符号 | 含义 |
|---|---|
| `I` | 门店当前可售餐品集合，`i ∈ I`，每项带价格 `p_i`（分）、品类 `c_i` |
| `x_i ∈ {0,1}` | 是否选择餐品 `i` |
| `N(i)` | 餐品 `i` 的官方营养向量 `(E, P, F, C, Na)`：能量 kcal、蛋白 g、脂肪 g、碳水 g、钠 mg |
| `B` | 预算上限（分） |
| `T = (E*, ε, P*, Na*, F*)` | 营养目标：热量目标、热量容差、蛋白下限、钠上限、脂肪上限 |

方案 `S = { i | x_i = 1 }` 的总量：

```text
cost(S)  = Σ_{i∈S} p_i
E(S)     = Σ_{i∈S} E_i        P(S) = Σ_{i∈S} P_i        Na(S) = Σ_{i∈S} Na_i
```

### 1.2 目标与约束

```text
minimize   cost(S)                     ← 省钱
maximize   score(S)                    ← 营养
subject to cost(S) ≤ B                 ← 预算硬约束
           Σ_{i∈S} [c_i = 主食] = 1    ← 品类规则（主食恰好 1 个）
           Σ_{i∈S} [c_i = 小食] ≤ 2
           Σ_{i∈S} [c_i = 饮料] ≤ 1
           Σ_{i∈S} [c_i = 甜品] ≤ 1
           N(i) 存在  ∀ i ∈ S          ← 营养未知的餐品不进入解
```

两个目标方向相反（更便宜通常意味着更少的营养），所以不存在单一最优解，
工程上正确的做法是输出**帕累托前沿**并让用户在取舍上做决定。

## 2. 营养得分

为了让两个目标可比，把营养侧聚合成一个 0~100 的分数：

```text
热量贴合 = clamp(1 − |E(S) − E*| / (E* · ε), 0, 1)              ε 默认 0.20
蛋白达成 = min(P(S)/P*, 1) ，若超过目标再加最多 0.15 的奖励
脂肪控制 = clamp(1 − max(0, F(S) − F*) / F*, 0, 1)              F* 默认 = E* × 0.35 / 9
钠惩罚   = min(1, max(0, Na(S) − Na*) / Na*) × 25

score(S) = clamp(100 × (0.40·热量贴合 + 0.45·蛋白达成 + 0.15·脂肪控制) − 钠惩罚, 0, 100)
```

**权重取值的理由**：

- **蛋白质 0.45 权重最高**：在外食场景下，蛋白质是最容易不达标、又最难靠「少吃」解决的指标；
- **钠用惩罚而不是权重**：钠超标不是「略微扣分」，而是踩到了健康红线，用惩罚项更贴近真实语义；
- **热量用区间而不是点**：一顿饭不可能精确命中 700 kcal，±20% 是合理的工程容差；
- 权重与容差全部可在 `src/solver.mjs` 的 `DEFAULT_WEIGHTS` / `DEFAULT_TARGETS` 中调整。

得分是**序数**而非基数：它用于方案之间的比较与排序，不代表营养学意义上的优劣程度。

## 3. 候选集裁剪

**为什么必须裁剪**：一份门店菜单可能有上百个餐品，即便有品类规则，全量组合也可达千万级。
而官方限流是 600 请求/分钟，意味着不可能对每个组合都调一次 `calculate-price`。

**做法**（`selectCandidates`）：按品类分桶后，在每个桶内取四个方向的并集，每方向取前 `k`（默认 6）；
营养未知但便宜的餐品另走一个 `cheapest-unknown` 方向，只用于「省钱底线」。

| 方向 | 意图 |
|---|---|
| 价格最低 | 保证省钱侧有解 |
| 蛋白质/元 最高 | 性价比最优的候选 |
| 蛋白质绝对值 最高 | 保证高蛋白目标可达 |
| 钠最低 | 保证低钠目标可达 |

**代价**：这是启发式裁剪，**不是全量穷举**，理论上可能错过全局最优解。
裁剪规模写进求解结果（`stats.candidateStats`，每个品类原有多少项 / 保留多少项，`--json` 可见）；
`--per-category` 可以调大以逼近穷举。⚠️ 逐品类明细目前**只进 JSON、未渲染进 SVG 战报**，
战报上只显示候选总数 —— 这是待补的呈现项。

## 4. 枚举与剪枝

按品类依次递归枚举，每个桶内按价格升序排列，当部分方案金额超过预算时**在该桶提前终止**
（升序保证了后续只会更贵）。同一方案用商品编码排序后的签名去重，避免因枚举顺序重复计数。

复杂度上界：`O(k_主食 × (1+k_小食+C(k_小食,2)) × k_饮料 × k_甜品)`，
默认 `k=6` 时实测（真实门店 118 项）约 26.5 万个方案、1 秒级完成；
演示菜单 28 项为 10,440 个方案，毫秒级完成。
**超过 40 万个方案时会截断**（`stats.truncated=true`），此时终端与战报会**显式告警**——
截断意味着结果是"部分枚举"下的最优，可能不是全局最优，不静默给出。

## 5. 帕累托前沿与推荐策略

设 `A` 为预算内可行方案集合。若方案 `a` 支配 `b`：

```text
cost(a) ≤ cost(b)  且  score(a) ≥ score(b)  且至少一项严格
```

则 `b` 不可能被理性用户选择。前沿即去掉所有被支配方案后的集合，按价格升序呈现
（价格升、得分严格升）。在演示数据（预算 30 元）下前沿有 8 个点。

在此之上给出三个**可执行**结论：

| 结论 | 定义 | 回答的问题 |
|---|---|---|
| 双赢推荐 | `argmin{ cost(S) : S 满足全部硬目标 }` | 达标的前提下最少花多少 |
| 营养上限 | `argmax{ score(S) : cost(S) ≤ B }` | 这些钱最多能买到多好的营养 |
| 省钱底线 | `argmin{ cost(S) : cost(S) ≤ B }` | 绝对最省是多少 |

> **「达标」= 用户硬目标全部满足**：热量落在目标区间内、蛋白质不低于下限、钠不超过上限，三项缺一不可，
> 且营养未知（`checks` 为 `null`）不算达标。**不使用复合得分门槛** —— 得分是自定义序数指标，
> 用它当"达标"会给出「用户要求 ≥30 g 蛋白、推荐却是 29 g」这类自相矛盾的结论。
> 若没有任何方案满足全部硬目标，退化为 `score ≥ minScore`，并把 `stats.qualifyingBasis`
> 置为 `score-fallback`，由终端与战报明示"已退化"。

三者可能重合，去重后输出 1~3 个方案（重合时少于 3 个属正常）。

### 5.1 成本口径：券后实付

上面的 `cost(S)` 不是菜单价合计，而是**券后实付**。官方券有两种形态，本项目只对**语义明确**的那一种计费：

```text
① 指定商品用券价（官方主形态）：
     couponSaving = max(0, 该商品菜单价 − 用券价)     仅当方案里含该商品
     例：麦旋风任选 9.9 元 → 方案含麦旋风（原价 14.5）时省 4.6 元

② 订单级满减（门槛 + 面额）：
     couponSaving = min(面额, 订单合计)              仅当 门槛 ≤ 方案菜单价合计
```

- 同一订单只核销**一张**券，所以取的是"省得最多"的那张，而不是叠加；
- 预算 `B` 卡的是**券前菜单价合计**——若允许券后实付卡预算，会出现"为了用满减券反而多花钱凑单"，
  与"省钱"目标相悖；
- **面额型券（"第二份半价"等）不计入计算**：其优惠与购买数量相关，名义面额 ≠ 真实优惠，
  硬当减免会算出错误结论，因此如实标注"未量化、不计入优惠"；
- 商品级券必须能**定位到方案内具体商品**（官方商品编码优先，其次名称匹配）才计费；
  定位不到的券宁可不算，也不猜金额；
- 无券或券不适用时，`cost(S)` 退化为菜单价合计，向后兼容。

在演示数据（预算 30 元）下，券使「双赢推荐」与「省钱底线」的实付从 ¥25.50 / ¥12.50 降到
**¥22.50 / ¥9.50**——"省钱底线"确实因为券而更低，而不是只把券印在报告里。

## 6. 与官方算价的衔接

本地用菜单价合计做求解（便宜、可枚举），然后只对最终的 3 个推荐方案调用
`calculate-price` 做官方核验，并把「本地价 → 官方价」的差异、用到的券与券面优惠写进战报。
这样既避免请求爆炸，又保证用户看到的最终金额有官方依据。

## 7. 已知局限

1. **启发式裁剪**可能错过全局最优（见 §3）；
2. **营养匹配失败**的餐品被整体排除，可能让某些高性价比套餐无法进入候选；
3. **品类按名称推断**：官方分类字段是菜单促销分区而非功能分类，故不采用；推断不到的商品落入「其他」被排除；
4. **套餐营养只累加 `isDefault` 默认组成项**，且累加值超出常理（>3000 kcal）时按"营养未知"处理；
5. **得分函数是自定义的**，不同人群（增肌 / 控糖 / 控钠）应有不同权重，当前未做人群预设；
6. **券只对语义明确的形态计费**（指定商品用券价），面额型与定位不到的券标注未量化、不计入；
7. **未考虑库存与售罄**：菜单返回即视为可售，实际下单时可能已售完。
